## 品牌定位

### 品牌

- **名称**：DevOps Gold
- **描述**：AI 原生 DevOps 与平台工程实践
- **作者署名**：Kevin Zeng（Benz）
- **主要语言**：简体中文；保留必要的英文专业术语，首版不建设双语站点。

### 核心读者

第一读者是正在推动团队从基础设施和流水线维护，走向平台产品与 AI 能力建设的 DevOps/SRE 团队负责人。第二读者是平台工程负责人和参与相关投入决策的研发管理者。

目标组织不按人数或企业规模划分，而按系统复杂度判断。重点关注主要使用云厂商 IaaS、ECS 等基础资源，并自行建设和维护 Jenkins、GitLab、容器平台、权限、发布及其他内部服务的环境。小团队只要已经面临跨系统协作、权限、上下文和治理问题，也属于目标读者。

### 核心论点

> AI 原生 DevOps 不是给每个工具接一个大模型，也不是推倒重建一套理想化的云原生平台；而是在既有自建系统之上，通过平台工程建立统一的能力契约、上下文、权限、护栏和反馈，使人和 Agent 都能安全地完成交付与运维。

推荐的渐进路径是：

1. AI 辅助人员完成工作；
2. AI 被封装为可复用、可治理的平台能力；
3. Agent 成为受权限和护栏约束的平台使用者。

差异化重点是第三阶段：不让 Agent 直接连接所有内部系统，而是通过 Agent 可操作平台使用经过治理的能力。

## 内容策略

### 内容支柱

1. **组织转型**：DevOps 团队如何走向平台工程与 AI 原生工作方式。
2. **Agent 可操作平台**：能力契约、上下文、权限、护栏、评测和反馈。
3. **存量系统平台化**：如何整合 ECS、Jenkins、GitLab、容器平台、IaC 和自建服务。
4. **可信与治理**：身份、权限、供应链、安全边界和生产责任。

容器网络、云平台和行业动态作为上述支柱下的具体案例，不另设首期栏目。

### 稿件类型

每篇文章必须且只能带一个稿件类型标签：

- `原创`
- `行业译介`
- `评论`
- `授权翻译`

同时可带一个或多个主题标签。首版复用现有 tags 能力，不新增 `contentType` schema 或定制展示组件。

### 译介与版权规则

行业译介不是逐段全文翻译。每篇译介至少需要说明：

1. 原文最值得关注的论点；
2. 原文依赖的组织、技术或市场假设；
3. 哪些结论适用于国内自建系统环境，哪些不适用；
4. DevOps/SRE 负责人接下来应该观察、验证或采取什么行动。

发布时遵守以下规则：

- 标明原作者、标题、发布日期和原文链接；
- 仅为评论需要引用必要片段，并明确标注；
- 未经许可不复制原文图片、图表、大段代码或长段正文；
- 只有在原文具有明确开放许可或取得作者授权时，才发布全文翻译；
- AI 可以辅助翻译，但作者必须核对技术含义，并对最终判断负责；
- 厂商文章需要标明商业立场，不能直接当作中立行业结论。

### 经历披露边界

作者可以抽象分享平台权限、云平台、容器网络与平台、可信平台、Agent 平台和 IaC 建设经验，但不得披露雇主、内部系统名称、未公开指标、用户数据或安全敏感细节。公开开源贡献可以附真实链接作为证据。

## 风险与应对

### 内容范围超过时间预算

支柱文章和清晰定位优先于视觉微调。若硬性验收未完成，保持预览状态并延后域名切换，不静默削减已确认范围。

### 译介版权或原创性不足

默认采用行业译介而非全文翻译，记录来源与许可；没有独立判断和国内适用性分析的稿件不发布。

### 大厂经历泄露敏感信息

使用匿名化场景和合成示例；不出现内部系统名、未公开数据、用户信息或可利用的安全细节。

### 生产域名切换失败

切换前记录 DNS 现状和回滚值；先通过 Pages 预览验收；切换作为单独确认的生产操作，失败时恢复旧记录。

### 预览域名与生产 canonical 不一致

预览阶段检查生成结果，但只有生产域名切换后才以 `devops.gold` 验证 canonical、RSS、sitemap 和 Open Graph 的最终行为。

### 外部服务不可用

Giscus、LinkedIn 或其他外部服务失败不得破坏正文阅读。验收时分别检查降级表现和链接正确性。
